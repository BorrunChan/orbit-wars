## 三、核心发现：proto1000 用 volume 取胜

bench 中观察 proto1000 vs 各 agent 的 launches/game：

| vs Agent | proto1000 launches | 我方 launches | 比例 |
|---|---|---|---|
| v98 | 1051 | ~100 | 10x |
| v105 | 914 | ~100 | 9x |
| v106 | 1239 | ~100 | 12x |
| v107 | 856 | ~100 | 8.5x |

**v98 一局发 ~100 次，proto1000 发 ~1000 次。** 不管我们加 coop / reinforcement，proto1000 仍 0/6。

### proto1000.py 真正的优势（重新阅读源码）

- **`MIN_SHIPS_MINE_ATTACK = 5`** — 任何 mine 有 5+ ships 就发射，无 shot_threshold filter
- **自定义 score 公式（line 24-51）** 直接计算距离/产能/敌方加成，**不经 shot_model 验证**
- **每个 mine 每回合扫描所有 target** — 几乎每回合每星都发射
- **"release havoc" mode（line 525）** — 占有 < 25% 时关闭 en_route 限制

**proto1000 哲学是 high volume + low filtering**。v98 哲学是 high precision + heavy filtering。**对一个 high volume 对手，filtering 是错的方向**。

### 为什么 v105/v106/v107 都退步？

- **v105 (coop)**：把 2 个 mine 都派去打 1 个 target，占用更多兵力，**减少了向其他 target 的并发**。在 2P 只有 2-3 个 mine 时，coop 比 single 浪费。
- **v106 (reinforce)**：抽取 ships 给 "doomed planet"，但 _doom_deficit 的判定可能过度悲观（基于 worst-case 威胁累加），**误诊断让我方少发了进攻**。
- **v107 (combined)**：两个负面相加。

## 五、关于 proto1000 的真实假设

之前总结 (_2.md) 说 proto1000 的优势是 "coop + reinforce + 60-tick threat"。**第 3 轮 bench 证明前两个都不是关键**。剩下的可能是：

1. **Volume**（已确认）：10x launches，靠数量碾压 v98 的"精准但少"打法
2. **Lower MIN_SHIPS threshold**：5 vs v98 的 ~20+（v98 有 buffered variant，candidates 一般 >= 20 ships）
3. **No shot_model filter**：v98 用 shot_model GBM 学的拒绝条件，proto1000 直接发——过滤掉了 v98 的"该发但不敢发"案例
4. **早期扩张速度**：proto1000 step 0 就开始扫所有 mine 派 5+ ships，v98 sim greedy 前期更保守

## 六、下次推荐方向（基于本轮反例）

### ❌ 不要做
- 任何 "加新的结构性 candidate 类型" — coop/reinforce 都证明不工作
- 任何在 v98 sim greedy 基础上 stack 的扩展 — 都引入回归
- 测 v107 4P bench — 2P 已经退步，4P 无意义

### ✅ 高优先级新方向

#### 1. v108: high-volume 哲学变革（最值得试）
完全重写 v98 的发射决策：
- 取消 shot_threshold 过滤（或大幅降低到 0.05）
- 取消 buffered variant
- min_ships 从 capture_cost 改为 max(5, capture_cost / 2)
- **每回合扫所有 (mine, target) 对，符合条件就直接发**（不过 sim greedy）
- 期望：vs proto1000 launches 提到 500-1000 量级

风险：可能在其他 opps 退步。但目标是 proto1000 这块硬骨头。

#### 2. 读 mlhybrid.py 看它怎么打 v98
v98 vs mlhybrid = 33% (2/6)。是 standard pool 里第二难的。可能 mlhybrid 也是 volume-based？如果是，那 v108 high-volume 也能帮 mlhybrid。

#### 3. 写一个 launch_rate adaptive shot_threshold
- 跨回合累计对手 launches
- 高 launch rate 对手 → 大幅降低 shot_threshold
- 低 launch rate 对手 → 保持 v98 现有 threshold
- 用 module-level state 跨回合保留
