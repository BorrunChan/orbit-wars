# Kaggle 评分机制与对手特征分析

> 基于 200+ 局真实 Kaggle replay（v69 → v95 部署期间），按机制 + 实战观察整理。
> Replay 原始数据在 `replays/`（96 个 typeIIIfairy 2P + 47 个中段 4P）和 `~/Downloads/episode-*.json`（253 个版本反馈）。

---

## 一、Kaggle TrueSkill 评分机制

### 1.1 不是简单"赢+X / 输-X"

Kaggle 用的是 **TrueSkill 贝叶斯评分**。每个玩家有：
- **μ (mu)**：当前 rating 估计值
- **σ (sigma)**：rating 不确定度（新号大、老号小）

每局结果根据**结果差额 + 双方 σ** 做贝叶斯更新。

### 1.2 影响每局得失分的 4 个变量

#### A. 对手 rating 差距（最大因素）

| 情况 | 大致变动 |
|---|---|
| 输给 +300 高分对手 | -3 ~ -8 |
| 输给同段 ±50 对手 | -10 ~ -15 |
| 输给 -300 低分对手 | -20 ~ -30（爆冷） |
| 赢 +300 高分对手 | +20 ~ +30 |
| 赢 -300 低分对手 | +3 ~ +8 |

#### B. 4P 是按"名次"算，不是赢/输二元

4P 局按最终名次（1/2/3/4）对四方做四方 TrueSkill 更新：

| 你的名次 | 大致影响 |
|---|---|
| 1st | +大涨 |
| 2nd | +小涨 / 微跌 |
| 3rd | 小跌 |
| 4th | 大跌 |

**所以"没拿第一"≠"输"**：
- 第 2 名丢的分 << 第 4 名丢的分
- 4P 拿稳第 2 也是赚的

这就是为什么 v95 的 "5W/9L" 里有些败局只丢几分、有些丢一二十分——区分在第 3 vs 第 4。

#### C. 你自己的 σ（不确定度）

- **新版本/连续波动大** → σ 大 → 涨跌都猛
- **跑了很多局趋稳** → σ 小 → 涨跌都温和

v86 冲到 1109 那段就是 σ 大、系统"快速重估"；之后连败丢得快也是 σ 还没收敛。

#### D. 同场对手组合（4P 特有）

4P 同场另外 3 人 rating 决定"期望名次"：
- 同场有 1 个 1400 + 2 个 900：你 1000 拿第 4，期望就不高 → 丢分少
- 同场是 3 个 800：你 1000 拿第 4，明显爆冷 → 丢分多

### 1.3 实操含义

1. **4P 必须优化"避免第 4"**，不是只优化"赢"
2. **不能输给低分对手**——这是真痛点
3. **版本切换初期 σ 大**，前 20-30 局波动剧烈是正常的，不要因短期跌就回滚
4. **峰值有运气成分**——v86 冲 1109 不代表 v86 比 v95 强

## 二、Kaggle 对手特征

### 2.1 对手分布（590 个 profile, `data/kaggle_opp_profiles.json`)

数据来源：`scripts/extract_kaggle_profiles.py` 从 238 个 replay 中提取，共 590 个唯一对手。

按风格大致分 3 类：

#### A. Swarmer（蜂群型）— **75% 败局来源**

**特征**：高 launches/game（>200），小舰队、密集发射，靠数量压制。

代表对手（极端样本）：

| 名字 | launches/game | 风格 |
|---|---|---|
| **LMaldaz** | **4944** | 极限 swarm，几乎每步都发 |
| **Rafael** | **3532** | 高频小舰队 |
| **typeIIIfairy** (#1) | 600-900 | 高质量 swarm（精准） |

**应对**：v83 起的 swarm-counter 是专门针对这类。两层触发（v93）+ 全面化（v95）已经把这类败局从 75% 降到 ~50%。

#### B. Structured（结构型）

**特征**：中等 launches（80-150），有明确扩张计划，会保留兵力做组合攻击。

代表：`structured.py` / `tactical2026.py` / `peak1103.py`（这些在 `opponents/`，是 Kaggle 公开 notebook 移植）。

**应对**：标准 sim greedy + V 模型本来就是为这类设计的，胜率较好（55-65%）。

#### C. Defender（防守型）

**特征**：低 launches（<60），靠占满本方扩张 + 反击。

**应对**：我方激进扩张通常能压死，胜率最高（>70%）。

### 2.2 顶段位（typeIIIfairy）的关键技术

从 96 个 2P 对局观察：

1. **旋转利用**：所有发射都计算行星到达时刻的旋转位置，利用 sun + 行星旋转改变弹道
2. **边沿控制**：先占据 4 个角落的偏远行星，逼对手长弹道
3. **节奏切换**：前 30 步缓慢扩张，30-60 步突然密集发射打乱对手
4. **保留兵力**：永远在本方行星留至少 8 ships 不发，防突袭

我方 v98 目前在 1、2 不足；3 有 swarm-counter 但被动；4 完全没做。

### 2.3 中段（~1300）4P 玩家观察

从 47 个 4P 对局：

- **第 1 名常见做法**：开局 3 步内确立扩张速度，60 步前不和任何人交手，60 步后专挑最弱的打
- **第 2 名常见做法**：和第 1 名相反——主动制造混战，让第 3、4 互相消耗
- **第 4 名常见错误**：太早和邻居死磕，被另一边渔翁得利

**v98 在 4P 偏向第 1 名做法**（避战 + 后期挑弱），所以 4P 32% 胜率主要靠拿第 1，第 2 比例低——这是潜在优化空间。

## 三、失分模式分析

### 3.1 时间窗口

按 80+ 局败局复盘，**失败窗口集中在 step 60-90**：

| 阶段 | 我方表现 | 对手表现 |
|---|---|---|
| 0-30 | 扩张同步、领先或持平 | 同步扩张 |
| 30-60 | 仍领先 | 开始施压 |
| **60-90** | **资源被对手追上、防御不及** | **集中发射** |
| 90-150 | 已落后，难翻盘 | 巩固优势 |

**根因假设**：60-90 步对手积累的小舰队同时到达，我方 SIM_HORIZON=16 看不到这一波。但 v99（horizon 10）反而更差，说明短 horizon 也不是解。

**未试方向**：mid-game adaptive buffer（step 60+ 强制留预备兵力）。

### 3.2 对手类型 vs 我方胜率

基于 v98 本地 bench + Kaggle replay 估算：

| 对手类型 | 局占比 | 胜率 |
|---|---|---|
| Swarmer (>200 launches) | 50% | 30-40% |
| Structured (80-150) | 30% | 55-65% |
| Defender (<60) | 15% | 70%+ |
| 其他 | 5% | 不定 |

加权平均 ~44%，与本地 bench 46% 大致吻合。

### 3.3 我方主要弱点

1. **被高速 swarm 淹没**（vs LMaldaz 类）—— 即使 v95 swarm 全面化也只有 25-30%
2. **4P 防 slot 2/3 时不如 slot 0/1**（player_idx 历史 bug 修了，但策略仍有差）
3. **中盘资源管理弱**（step 60-90 失血）
4. **不会主动"做局"** —— 4P 我们只会自己最大化，不会引导别人互殴

## 五、给 v99+ 的设计指引

基于上述分析，下一版本应该优先：

### 优先级 1：4P 名次保 2 优化
- 当前 V(state) 优化的是"赢"，应该改成"max(rank reward)"
- 添加：检测到自己已经第 2 时切换"保守巩固模式"，不冒险抢第 1

### 优先级 2：中盘防守缓冲
- step 60+ 强制保留 N 艘 ships 在主行星
- N 随 step 线性增长，到 step 100 强制保留 12

### 优先级 3：抗极限 swarm 上限策略
- 检测到对手 launches/game 估算 >300：进入"清扫模式"，所有候选改成击落在飞舰队
- 当前 v95 swarm-counter 在 LMaldaz 这种对手仍 0-20% 胜率

### 优先级 4：基于 profile 的 PFSP 训练
- 现有 `data/kaggle_opp_profiles.json` 590 个对手未充分利用
- PPO vs profile-sampled opponents（之前 PPO vs smart_swarmer 不外推就是因为只见一种对手）

### 不建议再做
- bigfleet / center bias / long horizon / MCTS / K 调整：见 `版本迭代历程.md` 已反复失败
- 离线 BC：已验证窄分布过拟合
