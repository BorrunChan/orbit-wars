```

       beats   ←----→   loses to
        ↑                       ↑
```

## 四、为什么不部署 v110

虽然 v110 头对头碾压 v98，**Kaggle 对手分布不是 1v1 vs v98 风格**。从 27 个真实 replay 看：

- 大多数对手 launch_rate 在 100-500 区间（structured / 中等 swarm）
- proto1000-style (>1000 LR) 是少数（约 5-10%）

部署 v110 = 拿一个**只擅长打 proto-style** 的 agent 去面对 90% structured 对手 = 净退步。

数学：
- v98 in Kaggle: 平均 ~47%
- v110 in Kaggle (估算): 33% 大头 + 100% 小尾 ≈ 35-40%
- v110 净更差

## 六、真正的下次方向：A7 + 双路由

唯一能利用 v110 优势同时保留 v98 强项的方法：**ensemble**。

```python
# Pseudocode for v111
def agent(obs):
    opp_launch_rate = estimate_opp_launch_rate(obs)  # 跨回合累计
    if opp_launch_rate > THRESHOLD:  # e.g. 5 launches/turn
        return v110_agent(obs)  # proto1000 style
    else:
        return v98_agent(obs)  # sim greedy
```

### 实现要点

1. **检测器**：跨回合 module-level state 累计敌方 launches，除以 step → launch_rate
2. **触发**：step ≥ 20 且 launch_rate ≥ 5 → 切 v110 模式
3. **冷启动**：step < 20 默认用 v98（更稳）
4. **代码组织**：v111.py 包含两套完整逻辑 + 路由层

### 风险

- launch_rate 估算的延迟 — step 20 才有 5 turn 数据，过晚？
- 已切到 v110 后切回 v98 会引发不一致（不同候选生成逻辑）— 应做 sticky decision
- 文件膨胀 — v111 ~ 1500 行（v98 + v110 全部 + 路由）

### 工程量

- ~3-5 小时实现
- 1 个 bench 验证：v111 vs 5 standard opps（希望同时 ≥ v98 在 structured + ≥ v110 在 proto1000）
