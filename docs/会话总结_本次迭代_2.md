## 二、本次发现（按重要性）

### 🚨 发现 1：4P 我们从未掉到 rank 3/4

来源：27 个真实 Kaggle replay 分析（用户提供）

```
4P 12 局：rank 1 × 4，rank 2 × 8，rank 3 × 0，rank 4 × 0
```

**"保 2" 方向 (v101/v102) 完全错** — v98 本来就稳第 2。4P 的优化目标应是 **"rank 2 → rank 1"**。

### 🚨 发现 2：proto1000.py 是本地真正的"杀手"

| Opp (2P) | v98 WR | opp launches/game |
|---|---|---|
| mlhybrid | 33% (2/6) | 322 |
| lb1224 | 67% (4/6) | 218 |
| structured | 67% (4/6) | 274 |
| **proto1000** | **0% (0/6)** | **1051** |
| orbitbotnext | 67% (4/6) | 272 |
| **总** | **14/30 = 47%** ✅ 匹配 Kaggle | — |

**proto1000 不是简单 swarmer** — 阅读源码 (opponents/proto1000.py) 揭示它有：
- **Coop attack**（多行星协同攻击同目标，line 607+）
- **Pre-computed reinforcement plans**（`get_reinforcement_plans`，line 322 — 主动算"需要 X ships 在 tick Y 之前到达"）
- **60-tick threat prediction**（vs v98 的 12-16 sim horizon）
- **Custom score formula**（line 24-51，加权距离/产能/敌方加成/总船数/ETA）
- **"Release all havoc"** 模式（line 525：当占有 < 25% 行星时全部开火）

**这就是 v98 输的具体破绽**——v98 缺这 3 个能力。要打 proto1000 必须加 coop attack + proactive reinforcement + longer threat horizon。

### 🚨 发现 3：本地造的所有 swarmer 都打不过 v98

写了 `swarm_light.py`/`swarm_medium.py`/`swarm_extreme.py` + bench 现有 `swarm.py`/`swarm2.py`/`smart_swarmer_v3.py`：
- **v98 vs 6 个 swarmer bot = 54/54 全胜（100%）**
- 但 Kaggle 数据说 v98 vs swarmer = 30-40%
- 本地 swarmer 太简单，没扩张阶段、被 v98 早期吞掉就再也发不了 launches

**本地 swarmer 测试集失败**。proto1000 反而是更好的"swarm 测试代理"，因为它兼具高 LR (1051) + 结构化能力。

### 🚨 发现 4：所有 threshold-tweak 实验全部 byte-identical

实验过的 agent 在 standard 4P pool 和 2P 单挑都和 v98 W/L 完全相同：

| Agent | 改动 | 4P bench | 2P bench |
|---|---|---|---|
| v101_rank_aware | rank=2 + 双 gap + skip neutral + +0.08 阈值 | **同 v98** | — |
| v102_no_attack_first | 同上 + 不攻 rank-1 | **同 v98** | — |
| v103_chase_first | rank=1 或 rank=2(gap<0.08, step<100) -0.05 | **同 v98** | — |
| v103b_chase_strong | rank=1 或 rank=2(gap<0.15, step<200) -0.10 | 未 bench | — |
| v104_early_swarm | 2P step<60 n_total>=4 elif | 同 v98（预期） | **同 v98** |

**5 个软调整 = 0 效果**。说明：
- v98 在 standard pool 已经是局部最优
- threshold tweaks 触发了但传播不到 final ranking
- 后续不要再做软 threshold 改动，要做结构性改变

### 🚨 发现 5：Medium swarmer (200-500 LR) 是 Kaggle 2P 真痛点

27 局 Kaggle replay 按 opp launch_rate 分桶：

| LR 区间 | 2P W/L |
|---|---|
| <200 | 2W/1L = 67% |
| **200-500** | **4W/5L = 44%** |
| 500-1000 | 0W/1L = (n=1) |
| 1000+ | 1W/1L = 50% |

extreme swarmer 反而 50/50。medium 是漏分主区。但 v98 现有 swarm 检测已经触发，问题是响应 (-0.06) 太弱。

## 五、下次会话推荐方向

### 🎯 高优先级（基于本次确证的事实）

#### 1. 攻克 proto1000.py - 加 coop attack
v98 vs proto1000 = 0/6。读 proto1000.py 后知道它有 3 个能力 v98 缺。最 ROI 高的单点：
- **Coop attack**：v98 candidate 生成时，对单个高价值 target 允许多 mine 同步发射（行星 A + B + C 一起发，目标行星 X）
- 同步：让 `find_angle_to_moving_planet` 算每艘队的 arrival tick，凑到接近
- 实现量 ~80-120 行（candidate 生成 + sim 评估同 target 多 launch）

#### 2. Proactive reinforcement
- v98 现有 `_doom_deficit` 只过滤，proto1000 主动算 `get_reinforcement_plans`
- 改动：把 `_doom_deficit` 升级为顶级候选生成器（"派 N ships 到 mine X 在 tick Y 前到达"）
- 实现量 ~50 行

#### 3. 把 27 个 Kaggle replay 的对手当训练/测试对手
- `opponents/replay_swarm.py` 已经有 wrapper（loads single replay）
- 改成多 replay 抽样，**实例化 27 个真实对手 bot**
- 把它们加入 bench pool — 这是**唯一能本地 bench 出 v98 真实弱点的方式**
- 实现量 ~30 行 wrapper + bench script

### 🚫 低优先级 / 不做

- ❌ 再做 threshold tweak（v101-v104 全 0 效果）
- ❌ 造更狠的 fake swarmer（造出来也打不到 v98 本质弱点）
- ❌ 部署 v101/v102/v103/v104（任何一个都和 v98 同 outcome，纯加复杂度）
- ❌ A7 ML 检测器（先有有效的 B 应对再做检测，不然 detect 了也没东西切）
- ❌ PPO/BC Phase 4 导出（用户明确说不外推）

### ⚠️ 注意点（给下次的我）

1. **每个 fact-gate edit/write 会冗余触发** — session 后段成本暴涨主要是这个。下次预先 `ECC_GATEGUARD=off` 启动
2. **27 replay attach 进 context 一次性烧 ~$50** — 想分析就用 Bash + python 脚本批处理，不要让原文进 context
3. **背景 bench 启动后 token cost ~0** — 在背景跑期间不要乱写代码，等 notification
4. **本次新发现的两个总结**：
   - 4P 优化目标 ≠ "保 2"，应是"争 1"
   - 本地 swarm 测试集要用 proto1000，不是 fake bot
