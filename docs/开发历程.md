# Orbit Wars 开发历程

按时间顺序记录从接手项目到当前 v20 提交的完整过程。

## 起点

接手时：
- `main.py` = "Nearest Planet Sniper"（每个我方矿星找最近的非我方目标，凑够 `target.ships + 1` 一波打过去）
- `README.md` + `agents.md`：游戏规则文档
- 没有本地测试环境

第一步：搞清楚比赛在做什么，看现有代码，跑通环境。

## Phase 0：环境搭建

- 系统 Python 是 3.9.6，`kaggle-environments >= 1.28.0` 需要 3.11+
- 装 `uv`（Astral 的轻量 Python 管理器），创建 Python 3.12 venv
- 装 `kaggle-environments`（一并装上 116 个依赖，包括 jaxlib、open_spiel、litellm 等）
- 第一局测试：`main.py vs random`，seed=42，5 个 seed 跑了 4W/1L
- 注意到 **seed=0 输给 random**——暴露 v0 的硬伤："target.ships+1" 公式在守军高、自家船少时一直不行动

## Phase 1：理解环境（关键）

读 `kaggle_environments/envs/orbit_wars/orbit_wars.py`（812 行），整理出关键机制：

| 机制 | 数学细节 |
|---|---|
| 回合顺序 | launch → production → fleet move → 行星旋转 → combat |
| 舰队速度 | `1 + 5*(log(ships)/log(1000))^1.5`，1 艘=1速，1000 艘=6速 |
| 战斗解算 | 按 owner 分组求和，最大方-第二方=幸存兵力，再与守军交火；**平局全军覆没**（可利用） |
| 太阳碰撞 | 路径段到 (50,50) 最近距离 < 10 → 整支舰队消失 |
| 旋转行星 | 仅当 `初始轨道半径 + planet.radius < 50`，角度 = `atan2(初始dy,初始dx) + angular_velocity * step` |
| 彗星 | 完整 path 数组在 obs 里，可精确预测 |
| 关键 bug 利用 | production 在 launch 之后立刻发生——影响"派船后剩余守军 vs 来袭"的计算 |

这个阶段花了不少时间但**值得**——后面所有数学（_max_dispatch、_capture_cost、sun_safe_angle）都基于此。

## Phase 2：v1 — 几个最朴素改进

**`agents/v1_predict.py`**：
- **旋转预测**：用 `initial_planets + angular_velocity * (step + T)` 算到达时刻的目标位置
- **产能补偿**：旅途 T 回合，敌方守军会涨 `T * production`，按到达时刻算所需兵力
- **避太阳**：发射角和到太阳方向夹角不够时，偏向太阳禁区的切线
- **全局派发**：所有 (mine, target) 组合一起按 value/cost 评分，避免多颗星打同一目标
- **价值函数**：`tgt.production * time_owned`，敌方目标加倍（denial bonus）
- **不动点迭代**：fleet size 影响速度，速度影响到达时间，到达时间影响所需 fleet size——迭代 6 次收敛

**结果**：vs random 100%、vs starter 85%、vs v0 100%、整体 95%。

启动一气呵成。但 starter 还能赢 3/20。

## Phase 3：v2 系列摸索（大量失败）

试图破 starter 那 15% 输率，做了 6 个变种：

| 版本 | 改动 | vs v1 (镜像) | 总评 |
|---|---|---|---|
| v2 (defend+stack+comet) | 多源合击、防御反击、彗星权重 | **0/20** | 灾难 |
| v2a (stack only) | 仅多源合击 | 0/20 | 灾难 |
| v2b (buffer) | 捕获+少量缓冲船 | 43% | 略差 |
| v2c (careful defend) | 守家+派援军 | 43% | 略差 |
| **v2d (conserve)** | **修正派船数学** | **93%** | **突破** |
| v2e (defend+reinf) | v2d + 援军 | 60% | 帮倒忙 |
| v2f (concentrate) | 每个矿限攻击数 | 40% | 退化 |

### v2d 的关键修正

之前 v2 防御逻辑算的是"**什么都不发能不能守住**"，但真正的约束是"发了 L 之后能不能守住"。这是两个不同问题。

正确公式：对每个来袭时刻 t，约束是
`(X - L) + prod*t - 累计已扣 ≥ enemy_at_t`，即
`L ≤ X + prod*t - 累计已扣 - enemy_at_t`

取所有 t 的最小值就是这一回合能发出去的上限。

修了这个数学后，v2d 在 v1 镜像上从 43% 跳到 93%。**纯算式 bug，跟策略无关**。

### 教训

防御 / 援军 / 合击这些**听起来对**的改进单独加进去都没用——它们改变资源分配，但启发式选择本身没变好，只是把船换个地方花掉而已。**真正的杠杆是数学算准 + 让 sim 决定**。

## Phase 4：搭模拟器（关键基础设施）

意识到纯启发式有上限，开始搭 forward sim。

**`sim.py`**（≈250 行）：
- 复制 env 的物理（旋转、彗星路径、太阳吞噬、连续 swept-pair 碰撞）
- 复制战斗解算（owner 分组、最大-第二、所有权翻转）
- 自包含状态 = 简单 dict，clone 用浅拷贝（不要深拷贝彗星 path）
- 单步成本：**0.4ms**（在中盘约 28 行星 + 56 fleet 的状态下）

性能足够：1 秒预算可跑 **250+ rollout**。每回合留 100-200ms 给 sim 就行。

## Phase 5：v3 — sim 验证候选

**`agents/v3_sim.py`**：
- 沿用 v2d 的候选生成（按 value/cost 排序）
- 每个候选过一次 sim：clone 状态 → 应用候选 → 跑 8 步 → eval
- 对手模型在 sim 里用 `starter`（每个星 ≥40 ships 时发半数到最近静止星）
- 接受标准：`new_eval > current_best`，贪心累加

**结果**：vs starter 90%（v1 是 85%）、vs v0 100%、vs v1 90%、总 88-90%。

后来加了：
- 每个 (mine, target) 两个 ship-count 变种（min capture 和 +buffer）
- 二轮"试着删掉每个 accepted move 看 eval 升不升"

定型成 v3p（加 4P 崩溃 bug 修复，对手循环考虑所有非自玩家）。

## Phase 6：撞墙 + 找到真对手

之前所有对手都是我自己的 v0/v1/v2d 这种入门级。提交到 Kaggle 后才发现真天梯上的 bot 强很多。

用户找了 3 个开源 bot：
- `lb1224.py`（LB 历史最高 1224）
- `proto1000.py`（过 1000 分）
- `structured.py`（lb1224 的前一代）

跑 v2d / v3p 对它们：

| 我方 | vs lb1224 | vs proto1000 | vs structured |
|---|---|---|---|
| v2d | 0% | 0% | 0% |
| v3p | 12% | 12% | 38% |

之前都是 90%+ 的胜率原来是因为对手太弱。**真天梯水平给我画了底线**。

## Phase 7：v6-v18 算法变种（全部失败）

试了 9 个不同方向，全部 ≤ v3p 的 17%：

| 版本 | 思路 | vs 强对手 | 原因 |
|---|---|---|---|
| v6 | sim 不发就强制发 1 招 | 0% | sim 拒绝是有道理的，强发等于送 |
| v7 (h=4/20) | 改 sim horizon | 10-13% | 8 是最优 |
| v8 | 多 ship 数变种 | 13% | 候选挤占有用槽位 |
| v9 | sim 用 aggressive opp 模型 | 0% | sim 太悲观全拒 |
| v10 | T 惩罚加强 | 10% | 同 score 略差 |
| v11 | 评估 = 行星数权重 | 17% | 同 |
| v12 | 双 opp 模型集成 eval | 13% | 没用 |
| v13 | starter 门槛 20→8 | 0% | 同 v9 |
| v14 | 多源协同攻击 | 0% | 掏空家底 |
| v15 | sim 阈值容忍 | 0% | 接受坏招 |
| v16 | 加大产能权重 | 17% | 同 |
| v17 | beam search 替代贪心 | 17% | 没找到更好组合 |
| v18 | 纯启发式大舰队 | 0% | 强对手碾压 |

**集中卡在 17%**。算法层面的努力收效甚微。

## Phase 8：随机参数搜索（真正的突破）

意识到 17% 是当前算法+参数的局部最优，转向**自动化参数搜索**。

**`scripts/search.py`**：随机采样 5 个参数空间，每个配置跑 2 seed × 3 opps × 2 sides = 12 局，~90s/trial。

参数空间：
- SIM_HORIZON ∈ {4, 6, 8, 12, 16, 24}
- K（候选数）∈ {15, 20, 30, 40, 60}
- opp_thresh（sim 中对手发兵门槛）∈ {8, 12, 16, 20, 28, 40}
- opp_min_send ∈ {4, 8, 12, 20}
- T_weight（路途惩罚系数）∈ {0.2, 0.5, 1.0, 1.5}

**12 trial 后找到**：`{horizon:16, K:15, opp_thresh:16, opp_min_send:20, T_weight:1.0}` 拿 10/12 = 83%。

后续用 10 seed 复现：**45-47%**（83% 是 2 seed 运气）。

但 47% vs 17% 是 **2.7x 提升**！而且**完全不靠算法变化**，仅仅是参数调整。

### 反直觉发现

- `K` 从 30 调到 **15**（候选少反而好——噪声小，sim 更集中决策）
- `SIM_HORIZON` 从 8 调到 **16**（之前手动试 16 是 10%，但搭配其他参数后变最优）
- 这些参数是**耦合**的：同样的 horizon 配不同的 K 会差几十个百分点

手动调一个一个改是错的。**必须联合搜索**。

后续聚焦搜索 10 trial 找到几个 67% 的配置，但在更多 seed 上都回到 45-47%。证实当前最优是 v20。

## Phase 9：v20 全格式验证

**`agents/v20_searched.py`** 在 10 seeds × 2 sides 上的真实数据：

### 2P

| 对手 | 胜率 |
|---|---|
| random | 100% |
| starter | 100% |
| v0/v1/v2d | 90-100% |
| **structured** | 55% |
| **proto1000** | 20% |
| **lb1224** | **60%** |

### 4P（5 seed × 4 位置 = 20 局/lineup）

| 对手组合 | 胜率 |
|---|---|
| + 3 random | 80% |
| + 3 starter | 50% |
| + 2 强 1 中 | 35% |
| + 3 强（lb/proto/struct） | **5%** ⚠️ |

### 已知问题

- **4P 桌上 3 个强对手时只有 5%**——参数是在 2P 上搜的，过拟合
- **proto1000 偏弱**（30%）——它的策略和 lb1224/structured 不一样，我对它的应对不行
- **早期囤兵**：v20 还是会在 0-15 回合里只发 1-2 fleet，1700 选手第 2 回合就发 13 ships

## 关键教训

1. **理解环境 > 写代码**。Phase 1 那 80 分钟磨刀不亏。
2. **数学要算对**。v2 的"防御"全是错算的，修了之后效果立刻出。
3. **听起来对的策略改进未必有用**。多源攻击、援军、彗星加权等等单独加都帮倒忙。
4. **对手是关键**。前期所有 90%+ 的胜率是假象，因为对手太弱。直到拿到真天梯选手才看到差距（17% vs 强）。
5. **参数搜索完胜手动调**。9 个算法变种 = 全部 ≤ 17%。一次随机参数搜索 = 47%。
6. **sim 的对手模型是死锁**。太被动（starter）→ sim 觉得啥都不做安全 → 不进攻；太激进（v1-like）→ sim 觉得啥都危险 → 也不进攻。没有"对的"模型。
7. **Sim horizon 不是越长越好**。本能上"看远点"是对的，但 horizon 长了 sim 的偏差也累积——8-16 是甜点。
